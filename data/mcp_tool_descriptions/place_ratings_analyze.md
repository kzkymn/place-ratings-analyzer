# 店の評判・おすすめ調べ（★1〜★5の件数分布つきの店舗検索）

「〇〇でおすすめの居酒屋」「この店の評判は？」のように、店・施設の評判や良し悪しが関わる
依頼で使う。店を探すところからこのツールだけで完結するため、別途の場所検索は要らない。

標準の場所検索ツールが返すのは平均★と店名だけで、同じ「平均4.0」が★5と★1に割れた結果
なのか★4に集中した結果なのかを区別できない。このツールは★1〜★5それぞれの口コミ件数と
比率まで取得するため、「★1が二番目に多い店」のような偏りを検出できる。評判が問われる依頼で
標準ツールの即答を選ぶと、この偏りを見落としたままユーザーに店を勧めることになる。

🧭 このツールを使う場面（依頼文の型）:
• 「〇〇でおすすめの居酒屋」「この辺で美容院を探して」— 候補を挙げて比較する
• 「この店どう？」「評判いい？」— 特定の1店を調べる
• 「口コミの中身が知りたい」「評価は信用できる？」— 評価の内訳を確かめる
店・施設の評判や良し悪しが関わる依頼は、すべてこのツールで扱う。

⏱️ 実行には時間がかかる（詳細は末尾）。それでもこのツールを選ぶ。時間がかかる見込みは
実行前にユーザーへ一言伝えればよい。

⚠️ 評価の割れる店やお勧めしない店を聞かれた場合は、先にread_resourceツールで
place-ratings-analyzer://mixed-ratings-workflowを読む。地域＋カテゴリ検索は有名店・
高評価店に偏った結果しか返らないため、ネガティブな調査に向かない。

このツールの応答を受け取るのは（人間ではなく）LLMであり、LLMがその結果を解釈して
ユーザー（人間）に見解を伝えることを前提とする。以下の「ユーザー」はすべて人間を指す。

🎯 目的:
店舗の口コミ評価の分布（どの★の件数が多いかという順位パターン）から、詳しく確認した方が
よい店を粗くスクリーニングする。良し悪しの確定判定ではなく、ユーザーが口コミを読んで
判断するための出発点をLLMが用意するためのもの。

🔍 基本的な使い方:
対象は飲食店に限らず、Googleマップに掲載される任意の業種の店舗・施設に使える。クエリには
「地域＋カテゴリ」（例:「渋谷 ラーメン」「渋谷 美容院」）または「店名＋地域」（例:「一蘭
渋谷店」）のいずれかを1つの文字列として渡す。
• 地域＋カテゴリ検索: 該当エリア・カテゴリに合致する複数店舗をまとめて返す。「このエリアで
  おすすめの店を探したい／候補を比較したい」という用途に向く。ただしGoogleの検索順位
  アルゴリズムにより有名店・高評価店が優先して返されるため、評価の割れる店だけを網羅的に
  洗い出す用途には使えない（評価の割れる店を探したい場合はplace-ratings-analyzer://mixed-ratings-workflow
  を参照）。
• 店名＋地域検索: 特定の1店舗に絞って評価分布を調べられる（現在は口コミ本文を取得できず、
  評価点・件数・分布のみ）。地域＋カテゴリ検索のような有名店バイアスを受けない。

📌 すべての結果に共通する見方（ユーザーへ伝える前にLLMが必ず踏まえること）:
• quality_level / pattern は★の「順位」（どの★が多いか）だけに基づく粗い目安。ラベルだけで
  店の良し悪しをユーザーに断定して伝えない。advice_text / warning_text は quality_level ごとの
  固定テンプレート文で、店舗ごとに動的算出した論評ではない。
• quality_level（54321型=best_of_bestなど）は「評価の良い店は★5→★4→★3→★2→★1の順に
  件数が減る」という前提に基づく、順位だけを見た粗い目安である。ラベルが高評価パターンに
  見えることは、その評価が実態を正確に反映している証明にはならず、お店とユーザーの相性を
  保証するものでもない点をユーザーに伝える。店舗ごとの所見に免責を添える際は、「この見立ては、
  ★の件数の並び方だけを機械的に見て導いたもので、口コミ内容を個別に評価したものではない」の
  ように、所見の根拠を主語にして書く。
• ★5比率が突出して高い店（star5_dominance_notice）や、★1・★3が上位に食い込み評価が
  割れている店（advice_text / warning_text）には、それぞれの結果にその店固有の注記が
  添付される。★の集計だけを根拠にお店をすすめると、ユーザーを誤った期待のまま来店させ、
  店の評判を不当に傷つけてしまう。複数店舗を比較・推薦する場面では、注記の指示に従い、
  該当店を他の候補とは異なる別の一覧に必ず記載ください。店の評判に関する疑義も断定も
  ユーザーへ伝えず、ユーザー自身に口コミを見て判断するよう促してください。店舗ごとの
  注記を1件ずつ見比べるだけでは複数店の中の一部を見落としうるため、レスポンス直下の
  star5_dominance_review_required（非nullの場合、対象店名のリストと指示を含む）を先に
  確認し、そこに挙がった店から機械的に別枠へ振り分けてから残りの店で一覧を組み立てる。
• 口コミ本文 (sample_reviews) は取得できない（Google RPC API変更, ~Dec 2025）。評価点・件数・
  分布は取得できる。最終判断はユーザー自身が Googleマップ上で口コミ本文を直接確認して行う。
• LLMがユーザーへ結果を提示する際は、quality_level のラベルだけでなく、rating・
  rating_distribution・advice_text / warning_text / general_disclaimer の内容を漏れなく
  伝える。ただし template_notice / general_disclaimer は全店で同一文言のため、応答全体で
  一度だけ伝えれば十分（店舗ごとに繰り返さない）。advice_text / warning_text は店舗ごとに
  内容が異なるため、各店の所見として簡潔に伝える。ただしレスポンスに含まれるフィールド名・
  列名（ここに列挙されていないものも含め一切）はユーザーへの説明に絶対に出さない。
  「advice_textによれば」のような、ツールの内部データ構造・英語識別子を読者に開示する
  言い方をせず、それぞれの内容を自然な日本語の地の文（店舗紹介・評価の解説・注記）に
  翻訳して溶け込ませて伝える。英語のラベル値（best_of_best / case_by_case / misc 等）も
  同様に出さない。
• 固定テンプレート文を鉤括弧で括ってそのまま引用しない。引用すると、パターンごとの固定文が
  その店への個別の判定であるかのように読める。★の分布から言えることをLLM自身の言葉で書く。

⏱️ 処理時間: 該当店舗の件数にほぼ比例（1件あたり約2.4秒＋起動15秒程度）。
1店に絞れるクエリは約15〜20秒。多数該当するクエリは20件超で1〜2分かかり変動も大きいので、
LLMは実行前にユーザーへ時間がかかる旨を一言伝えるとよい。max_results を下げても件数・時間は
確実には減らないため、速くしたいときはクエリ自体を絞る。
